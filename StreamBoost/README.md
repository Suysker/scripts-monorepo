# 流媒体加速缓冲 🚀

> **通用流媒体加速缓冲脚本：扩大缓冲、并发预取、内存命中、在途合并、站点级启停，一把梭！**
> 适配 **HLS.js** 播放器。

## 🐣 这个脚本为什么会诞生？

在线看剧/直播时，很多站点的**缓冲策略非常保守**：只往前拉一小段，稍微网络抖一下就**卡**；有些站点还把 HLS 片段加载做成了**串行**（同时只跑一个请求），遇到高 RTT/限速就雪上加霜。
更糟的是，部分站点自定义了 Loader/XHR，导致**明明 HTTP/2 支持多路复用，却看起来只有一个在下载**；偶发 403/CORS 也会让播放器反复重试、白白等很久。
这些体验都很烦躁，于是就有了 **StreamBoost**：在不侵入页面业务逻辑的前提下，接管片段的**预取与缓存策略**，把能并发的并发起来，把能命中的命中起来，把没必要的在途请求**及时中止**，尽量把“卡顿感”消掉。

---

## 🌟 主要功能

* **并发预取（真正并发）**：按设置的目标时长持续提前下载，每批默认安排 12 个片段，完成后继续下一批；播放器暂时停止填充缓冲时，脚本仍可继续下载目标范围内的内容。
  普通配置按所选策略依次尝试 XHR、原 Loader、fetch；发现自定义 Loader 或请求 setup 时，预取只走原 Loader，保留站点鉴权与请求语义。认证/限流失败不连续重试其他 transport。
* **在途合并**：播放器要的片段如果**已经在下载**，短暂等待直接复用结果，避免重复请求。
* **复用已下载的内容**：正常播放和提前下载的完整片段共用一份缓存。在缓存未被淘汰时，拖动进度、切换清晰度后切回、播放器重新绑定视频，都尽量复用已有内容，减少重复下载。
  优先保留播放位置附近的内容，即使播放器已经接收也保留下载副本，方便播放器清缓冲后恢复。超过缓存参考容量时，先清理已播放或目标范围外的内容；目标范围内的完整片段仍可继续缓存。
* **淘汰过时在途**：拖动进度、切换清晰度或换源时，停止已不在下载目标范围内的预取，省流量也省时间。
* **缓冲增强（HLS）**：提高播放器的提前缓冲目标，保留网站原本更大的设置。遇到容量不足时先降低目标；播放继续、旧内容释放后，再小幅尝试恢复，再次遇到限制就延长等待，避免反复撑满。直播保留原有的同步策略。
* **真正全局的设置**：参数、全局开关与 Debug 状态保存在脚本管理器的 GM 存储中，同一脚本安装下的所有匹配网站共享。
* **按当前主机名启停**：主机名禁用策略与全局开关彼此独立；只跳过命中的文档主机名。
* **iframe 配置一致**：顶层页面、同源 iframe 与由 `@match` 独立注入的跨域 iframe 都读取同一份全局配置。
* **调试日志**：可查看缓存命中、失效原因和播放器缓冲状态；最近的诊断记录有数量上限，不记录媒体完整地址或请求凭据。

## 📥 安装方式

1. 安装浏览器扩展 **Tampermonkey**（或兼容脚本管理器）。
2. 打开 `StreamBoost/StreamBoost.js`，点 **Raw** 进行安装（或在 Greasy Fork 页安装）。
3. 刷新含播放器的页面即可体验加速。

脚本源码地址（Raw）：
`https://raw.githubusercontent.com/Suysker/scripts-monorepo/main/StreamBoost/StreamBoost.js`

> 兼容：Chrome / Edge / Firefox（现代版本）。Safari 因扩展限制可能需要额外授权。

## ⚙️ 菜单与控制

安装后，在 Tampermonkey 图标的页面菜单里可见：

* `🔌 全局状态（启用/停用）`
* `⛔ 停用当前主机名` / `✅ 移除当前主机名停用规则`
* `⚙️ 打开参数配置页`
* `🐞 Debug 日志（启用/停用）`

`全局状态`、`Debug` 和参数配置由所有匹配网站与 iframe 共享；`当前主机名` 命令只改变当前文档主机名的禁用策略。规则忽略协议和端口、精确区分不同子域名，并支持 IPv4 / IPv6 主机名。跨域播放器 iframe 是另一个文档主机名，不会因为顶层网站被单独禁用而自动禁用。

> 设置保存或菜单切换后不会热修改已经创建的 Hls 实例。请刷新所有需要应用新配置的顶层页面或 iframe；新打开的匹配页面会直接读取最新配置。

## 🛠 全局参数配置（GM 存储）

请通过菜单里的**参数配置页（悬浮可视化表单）**修改参数。配置集中保存在脚本管理器的 GM 存储中，不属于任何网站的网页存储；在网站 A 保存后，网站 B、同源 iframe 和跨域 iframe 刷新后都会使用同一份配置。

参数页提供滑动条、选项按钮和启用/停用按钮，并按 `预取并发`、`缓冲与内存`、`请求策略+常规开关` 分组。`恢复默认` 只恢复面板中的运行参数；全局启停和主机名禁用策略仍由各自的菜单命令管理。完成修改后需点击 `保存全局配置`，再刷新需要生效的页面。

### 控制项与作用域

| 控制项 | 持久化作用域 | 实际作用 |
| --- | --- | --- |
| 全局状态 | 当前脚本安装全局 | 关闭后，所有匹配网站和 iframe 刷新时都不再注入 StreamBoost |
| Debug 日志 | 当前脚本安装全局 | 所有匹配网站和 iframe 刷新后统一开启或关闭日志 |
| 参数配置页 | 当前脚本安装全局 | 所有匹配网站和 iframe 读取相同参数 |
| 当前主机名停用/启用 | 全局主机名策略列表 | 只决定与当前文档主机名匹配的页面是否注入，不改变全局状态 |

### 参数配置页（常规开关）

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| 并发预取 | 连续向前预取后续片段 | 启用 |
| 内存命中 fLoader | 优先复用页面上下文中的 LRU 缓存和在途结果 | 启用 |

### 参数配置页（进阶参数）

| 参数 | 范围/说明 | 默认值 |
| --- | --- | --- |
| 每批预取片段数 | `0-60`；完成后继续下一批，不截短目标时长；`0` 关闭预取 | `12` |
| 页面上下文总并发上限 | `1-16`；在每个顶层页面或 iframe 的独立运行上下文内执行 | `4` |
| 单资源 Origin 并发上限 | `1-16`；限制单个片段资源 Origin 的并发 | `4` |
| 预取超时 | `1000-120000 ms` | `15000 ms` |
| 在途复用等待 | `0-10000 ms` | `500 ms` |
| 预取策略 | XHR、Hls Loader 与 fetch 的尝试顺序 | `xhr-hls-fetch` |
| 预取目标 | `5-7200 秒`；与下面两项同步，决定从当前位置向前下载多久 | `600 秒` |
| 前向目标 | `5-7200 秒`；调整时同步另外两项，也用于播放器缓冲目标 | `600 秒` |
| 最大缓冲目标 | `5-7200 秒`；调整时同步另外两项，也用于播放器缓冲目标 | `600 秒` |
| 回看缓冲目标（至少） | `0-1800 秒`；不降低站点已有的更高值 | `180` |
| 缓存参考容量 | `16-512 MB`；超过后优先清理已播放或目标范围外的内容，目标范围内可暂时超出；不包含播放器缓冲和临时响应副本 | 按设备内存取 `64/128/192 MB` |
| MSE 缓冲目标 | `16-512 MB`；HLS `maxBufferSize` 至少提高到该值且内部最低为 `60 MB` | 按设备内存取值；兼容已保存的内存配置 |
| 实验性自适应预取 | 连续失败降低投机并发，连续成功缓慢恢复；省流量模式停止投机预取，直播缩短预取范围 | 关闭 |

**三个时长默认都是 600 秒，并始终保持一致。** 调整其中任意一项，另外两项会同步为相同的秒数；每批片段数只影响下载批次。暂停视频时仍会尝试填满当前目标范围，视频结尾处停止。原来使用默认时长的设置会转为三个 600 秒；如果你曾自行调整时长，三个值会统一为原来实际生效的较大值。直播只下载当前清单中可用的内容，保留原有直播预取策略。

虽然这些参数全局持久化，但预取队列、在途表和缓存分别存在于每个页面上下文中。因此，“页面上下文总并发上限”和缓存参考容量不是跨标签页、跨 iframe 汇总的浏览器级限额。点播初始化时，播放器的前向和最大缓冲目标至少达到设置的提前缓存时长，保留网站原本更大的设置。清单加载时会恢复被覆盖的目标；如果当前视频已经出现缓冲容量不足，则先保留播放器的调整。持续播放并释放旧内容后，脚本才逐步尝试恢复，且不超过该视频初始化时的目标；清晰度切换或重新加载清单不会跳过等待。真正换视频时重新评估。回看和 MSE 目标只向上调整，不改写直播同步参数。

### 快速验证（手动）

1. 在网站 A 打开参数页，将“页面上下文总并发上限”等参数改成容易辨认的值，保存并刷新。
2. 打开无关的网站 B，确认参数页显示同一值；刷新 HLS.js 播放页并用 Debug 日志确认运行参数一致。
3. 在含跨域播放器 iframe 的页面刷新顶层页面，确认 iframe 的 StreamBoost Debug 日志也使用同一份参数。
4. 用“停用当前主机名”确认只跳过该主机名，再用“全局状态”确认所有匹配网站和 iframe 刷新后都停止注入。

## ✅ 适用范围与限制

每个播放器分别管理下载任务。全屏和窗口大小变化不会主动清空缓存；拖动进度或切换清晰度会调整接下来要下载的内容，已下载且仍有效的片段继续保留。真正换源或资源身份变化时会隔离旧数据，不会把另一段视频的缓存混进来。

普通点播播放器在同一个视频元素上重建时，可在 30 秒内复用已确认属于同一资源的缓存；这部分缓存仍受参考容量和清理规则管理。直播、使用特殊请求方式的播放器，以及无法确认资源相同的情况，不跨实例复用。无法可靠缓存的请求继续由播放器原有的下载方式处理。关闭内存命中也会停止提前下载，正常播放不受影响。

实际加速效果受站点、网络和设备影响；自定义播放器若在脚本接管前改写了下载逻辑，可能无法被完整识别，不保证兼容。实验性自适应策略默认关闭。

* **适用**：采用 **HLS.js** 的站点（含以 video.js 方式集成的 HLS）。
* **限制**：DRM/加密媒体、Safari 原生 HLS（非 MSE/Hls.js）不在接管范围。
* **网络策略**：跨域仍受 CORS 约束；原生 XHR 会遵循站点 `xhrSetup`（可设置 header / `withCredentials`）。
* **生效时机**：设置不会热更新现有 Hls 实例；保存或切换后需要刷新相关页面或 iframe。
* **配置边界**：GM 配置在同一脚本管理器安装内全局共享，不代表不同浏览器、浏览器配置文件或设备之间自动同步。
* **配置来源**：运行参数从脚本管理器的 GM 存储读取；未保存配置时采用统一的全局默认值，不读取网站自身的网页存储参数。
* **主机名边界**：当前主机名禁用忽略协议和端口、区分子域名；跨域播放器 iframe 需按其自身主机名管理，或使用全局开关统一停用。
* **资源边界**：并发、在途请求和 LRU 缓存按页面上下文独立执行，不是浏览器级统一资源池。

## ❓常见问题（FAQ）

* **设置了 600 秒，为什么缓冲不到 600 秒就停了？**
  600 秒是下载目标，实际进度仍受网络、片源和浏览器可用内存影响。原有缓冲条保持播放器自身的显示；脚本已经下载、但浏览器尚未接收的内容，不一定显示在条上。这些内容仍可在后续播放时复用。长视频中的 600 秒占整条进度条的比例也可能很小。
* **全屏后为什么缓冲条可能变化，画面也可能短暂停顿？**
  播放器已处于选定清晰度、当前位置也有可播放内容时，脚本会忽略重复选择同一档位，避免全屏或窗口变化引发无谓的清缓冲。真正切换清晰度、首次选档、换源或没有可播放缓冲时，仍由播放器正常处理。
  真正切换到其他清晰度时需要对应的视频内容，仍可能短暂停顿；播放器重建后也需要重新处理缓存数据，不能保证所有全屏操作都完全无停顿。已经下载的分片仍需由播放器接收和处理，下载缓存不等于浏览器播放缓冲。网站用重复选择同一档位强制重载的行为，在上述正常缓冲条件下也会被忽略。
* **下载过的内容一定能一直保留吗？**
  不会。超过缓存参考容量时，会先释放已播放或当前目标范围外的内容，保留接下来要用的片段；当前目标范围内的完整片段可以暂时超出参考容量。换源、直播窗口过期或离开页面也会清理相关内容。缓存用于减少重复下载，不是离线保存。
* **看起来还是“串行”？**
  有些站点/中间层在 HTTP/2 下会把多请求显示为“挂起”，其实是多路复用；开启 `🐞Debug` 可看到 StreamBoost 的并发占位与在途数量，更准确。
* **403 / CORS 怎么办？**
  普通配置按所选策略预取；站点提供自定义 Loader 或请求 setup 时使用原 Loader。跨域请求仍需资源服务器允许。
* **会不会很占内存？**
  会占用内存，且高码率视频在提前缓存范围内可能超过“缓存参考容量”。脚本会优先回收已播放或目标范围外的内容，不会为了更远的片段淘汰附近未播放的数据。播放器自己的缓冲、网络响应和临时副本还会额外占用内存；浏览器内存不足时仍可能限制实际下载量。未保存容量设置时，脚本按设备报告的内存等级选择默认值；这个信息不代表实时剩余内存，也不保证浏览器能容纳目标时长。已保存设置不会被设备检测覆盖。需要减少脚本提前下载量时，可调低任意一个时长设置，另外两项会同步变化；网站自身较大的播放缓冲设置仍会保留。
* **为什么保存后当前视频没有立即变化？**
  已创建的 Hls 实例和 Loader 无法安全热替换。刷新顶层页面或对应 iframe 后，新实例才会使用最新全局配置。
